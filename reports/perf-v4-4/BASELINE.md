# V4.4 性能基线（真机实测）

测量环境：Waveshare ESP32-P4-WIFI6-Touch-LCD-7B，COM5，1024×600 MIPI-DSI，
LVGL 9.5，ESP-IDF 5.5.5，`ESP_LV_ADAPTER_ROTATE_180` +
`ESP_LV_ADAPTER_TEAR_AVOID_MODE_TRIPLE_PARTIAL`，TF 卡已插、6/6 素材包已加载、
NVS 存档正常（非安全模式、非无卡模式）。

被测镜像：`firmware/build/os/little_world.bin` 2,358,000 B
（0x23FAF0，含本轮 `rpg` 探针命令），经 `tools/flash_v4_safe.ps1 -Stage app`
只写 0x10000 应用分区，NVS/分区表未触碰。

测量工具是设备自带的三个控制台命令，全部读真机状态，不是仿真：

| 命令 | 含义 |
| --- | --- |
| `sched` | LVGL 任务里那个 20 ms 的 OS tick 定时器的**实际调用间隔**。它等于「界面多久有機會动一次」，是用户能感觉到的响应粒度。 |
| `fps` | 适配层 `display_manager` 在 flush 完成时累加的**完整帧提交数/秒**。 |
| `rpg` | RPG 页的**逻辑格、插值点、控件真实 x/y** 三层同时输出。 |

## 1. 页面级基线：同一个 20 ms 定时器，各页面跑成什么样

每行都是 `sched reset` 之后连续 5 秒采样。

| 页面 | page | avg_gap | max_gap | 相对 20 ms | 折算 |
| --- | --- | --- | --- | --- | --- |
| 桌面（双角色待机） | 0 | 30–37 ms | 434–452 ms（仅启动一次） | 1.6× | ≈27–33 次/秒 |
| 音乐 | 6 | **21 ms** | 85 ms | 1.05× | ≈48 次/秒 |
| RPG | 9 | **120 ms** | 123–137 ms | 6× | ≈8 次/秒 |
| 世界 | 1 | **139–151 ms** | 319–532 ms | 7× | ≈7 次/秒 |
| 宠物 | 8 | **777 ms** | 846 ms | **39×** | **≈1.3 次/秒** |

同一块板、同一个固件、同一份存档，只是换页面，代价差 37 倍。

**结论（可以负责任地说）：当前「整体很卡」不是单一原因，而是至少两种完全不同的
问题叠在一起。**

- 音乐页 21 ms 说明显示链路本身不慢：DSI 60 Hz、三缓冲、PPA 未启用也能跑到
  接近定时器周期。**所以「硬件达不到」这个借口在音乐页是不成立的。**
- 宠物页 777 ms 说明有页面每帧在做一件耗时接近四分之三秒的事。这个量级不可能
  是绘制本身，只可能是**同步 I/O 或整页重排**卡在 LVGL 线程里。
- 世界页、RPG 页 120–150 ms 是中间档：每帧几十毫秒级的工作量。

## 2. 帧提交率（`fps` 命令）

| 场景 | fps |
| --- | --- |
| 桌面双角色待机 | 4 / 6 / 10 / 15（多窗口采样，典型 10–15） |
| 世界页 | 3 |
| 宠物页 | 未完成（该页 `sched` 已 777 ms，fps 必然 ≤2） |

`fps` 只统计**至少提交了一次 flush 的秒**，所以「静止画面」会读成 0 或很小的数。
判断「动没动」必须同时看 `anim` 的帧索引和两张截图的 SHA-256，不能只看 fps。
这一条已经写进 V4.3 的 PERFORMANCE.md，本轮继续适用。

## 3. RPG 页：插值在算，但屏幕没跟上

`rpg` 命令连续采样（同一次移动中）：

```
rpg 0: tile=4,6 point=4.00,6.00 screen=172,189 moving=0
rpg 0: tile=4,6 point=4.89,6.00 screen=172,189 moving=1
rpg 0: tile=4,6 point=4.89,6.00 screen=222,188 moving=1
rpg 0: tile=6,6 point=6.31,6.00 screen=222,188 moving=1
rpg 0: tile=7,6 point=7.74,6.00 screen=302,188 moving=1
```

读法：`point` 是本次改动新增的连续插值（单位是格，可以带小数），`screen` 是
LVGL 控件真实的 x/y（= `anchor - pivot`，144 px 偏移，与格坐标一一对应）。

- `point` 确实是连续的（4.00 → 4.89 → 6.31 → 7.74），说明**插值逻辑本身正确**。
- `screen` 每次跳 50–80 px，即**整整一秒只更新两三次**。160 ms 一跳、每跳一格，
  这就是用户说的「瞬移」。
- 原因不是插值算错，而是该页 `sched` = 120 ms：**LVGL 定时器每 120 ms 才被跑
  一次，插值得再细也画不出来。**

因此：**RPG 瞬移 = 旧的「整格吸附 + 140 ms 补间」 + 新的「页面级定时器饥饿」两个
成因叠加**。前者本轮已从代码里删掉，后者才是肉眼看到的那一下跳动。

## 4. 已排除的原因

- **不是主任务栈溢出**：V4.3 已把 `CONFIG_ESP_MAIN_TASK_STACK_SIZE` 提到 32768，
  本轮重启全部干净（`previous ended cleanly`，未进安全模式）。
- **不是 SD DMA 内存不足**：V4.3 已给 `bsp_sdcard->host.dma_aligned_buffer` 预留
  自适应 32 KiB，本轮 `resources: reads=2104 failures=0`。
- **不是缓存太小**：V4.3 已改 16 槽 / 4 MiB，本轮 `cache resident=3145728`。
- **不是全局调度问题**：音乐页 21 ms 证明 LVGL 任务本身能跑满。

## 5. 下一步（按证据顺序，不靠猜）

1. 宠物页 777 ms：先确认是 I/O 阻塞还是整页重排。方法和结果写进
   `SPRITE_CACHE.md`。
2. 世界页 / RPG 页 120–150 ms：`refresh()` 每 20 ms 无条件调用
   `lv_obj_move_to_index()` 两次（`lw_rpg_view.c:103-104`），以及精灵控件
   288×288 的画布远大于实际像素（男 108×212、千千 104×202）。这两项都要做
   单变量对照。
3. 桌面 30–37 ms 已经是目前最好的页面，但仍未达到 20 ms 目标，说明即使最轻的
   页面也还有约 10–17 ms 的固定开销，需要 `DISPLAY_BENCHMARK.md` 的单变量矩阵
   来定位（tear-avoid 模式 / PPA / 绘制单元数）。
